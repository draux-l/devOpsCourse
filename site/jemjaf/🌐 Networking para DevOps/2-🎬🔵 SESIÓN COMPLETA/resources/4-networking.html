⚠️ ANTES DE EMPEZAR: IPv4 vs IPv6

Todo lo que veremos en este curso es sobre IPv4. Es la versión que usa el 90%+ de la infraestructura actual.

La mayoría de infra enterprise aún usa IPv4. Lo dominarás primero.

⛔ 5 IPs QUE UNA SUBNET TE QUITA

Sin importar qué nube uses, cada subnet reserva las primeras y últimas IPs. No puedes asignarlas a recursos.

Ejemplo con subnet 10.0.1.0/24 (256 IPs totales)
10.0.1.0 Dirección de red Identifica la subnet. Nunca asignable.
10.0.1.1 Router / Gateway AWS la reserva para el gateway de la VPC.
10.0.1.2 DNS Servidor DNS de la VPC (Base + 2). Azure usa la misma convención.
10.0.1.3 Reservado Reservado para uso futuro por AWS.
10.0.1.255 Broadcast Última IP. AWS no usa broadcast pero la reserva.

💡 /24 = 256 - 5 = 251 usables  |  /28 = 16 - 5 = 11 usables  |  /16 = 65,536 - 5 = 65,531 usables

🧱 SEGMENTACIÓN: ¿POR QUÉ DIVIDIR?

🏦 Analogía

Un banco no pone la bóveda al lado de la entrada. Cada zona tiene acceso diferente y restringido. Tus subnets igual.

❌ Sin Segmentación — Todo en una red
😈 Atacante
HACK
🗄️ Base de datos
ACCESO DIRECTO
  • Un solo punto comprometido = todo expuesto
  • La DB es accesible desde Internet
  • Movimiento lateral libre del atacante
✅ Con Segmentación — Zonas aisladas
🌐 Internet
HTTP
:443 OK
⚖️ ALB
Subnet Pública
  • Solo el ALB está expuesto a Internet
  • App servers en subnet privada
  • DB solo acepta tráfico de la app (por SG)

Principio de mínimo privilegio en red: Cada componente solo habla con quien necesita. La DB solo recibe tráfico del SG de la app en el puerto 5432.

🚧 FIREWALLS: EL GUARDIA DE SEGURIDAD

👮 Analogía

El firewall es el guardia de una discoteca: decide quién entra, por qué puerta, y si llevan algo prohibido.

Qué filtra
  • IP Origen: ¿de dónde viene? (0.0.0.0/0 = todos)
  • IP Destino: ¿a dónde va?
  • Protocolo: TCP, UDP, ICMP
  • Puerto: 80, 443, 22, 3306...
  • Dirección: Inbound / Outbound
Ejemplo de reglas
✅ ALLOWTCP :4430.0.0.0/0
✅ ALLOWTCP :2210.0.0.0/8
✅ ALLOWTCP :543210.0.10.0/24
❌ DENYALL0.0.0.0/0
Las reglas se evalúan en orden. La primera que coincide gana.

🛡️ SECURITY GROUPS vs NACLs (AWS)

Security Group (SG) — Nivel Recurso
  • Stateful: permite entrada → respuesta sale automáticamente
  • Solo reglas de PERMITIR
  • Se asigna a: EC2, RDS, Lambda, ELB
  • Puedes referenciar otros SGs como origen
Permite TCP :5432 desde sg-app-servers
→ Solo la app puede hablar con la DB
Network ACL (NACL) — Nivel Subnet
  • Stateless: debes permitir entrada Y salida
  • Reglas de PERMITIR y DENEGAR
  • Se asigna a la subnet completa
  • Evaluación en orden numérico (100 → 200 → 300)
100: DENY TCP de 1.2.3.4/32 any
→ Bloquear IP maliciosa en toda la subnet
🔑 Cuándo usar cada uno

Empieza con Security Groups (más fáciles). Usa NACLs cuando necesites bloquear IPs específicas a nivel de subnet (ej: respuesta rápida a un ataque).

🤝 PEERING: CONECTAR REDES PRIVADAS

🏘️ Analogía

Peering = abrir una puerta secreta entre dos edificios. Tráfico privado, sin salir a la calle pública (Internet).

☁️
VPC-A (Prod)
10.0.0.0/16
VPC Peering ✅
⇌
Tráfico privado
🔧
VPC-B (SharedSvc)
10.1.0.0/16
✅ Ventajas
  • Sin Internet — tráfico interno privado
  • Latencia baja y predecible
  • Sin costo de NAT Gateway
  • Funciona intra- e inter-región
❌ Limitaciones CRÍTICAS
  • No transitivo: A↔B, B↔C ≠ A↔C
  • Sin CIDR overlap — bloqueante
  • Requiere route tables en ambos lados
  • Alternativa escalable: Transit Gateway

⚠️ SOLAPAMIENTO DE CIDRs: EL ERROR FATAL

📬 Analogía

Dos edificios con el mismo número de apartamento 302. El cartero (router) no sabe a cuál ir. Resultado: fallo total.

❌ OVERLAP — Peering imposible
VPC-A: 10.0.0.0/16
VPC-B: 10.0.0.0/16
VPC-C: 10.0.5.0/24 ← dentro de VPC-A
La consola de AWS mostrará error inmediatamente. Azure y GCP igual.
✅ SIN OVERLAP — Peering OK
Prod: 10.0.0.0/16
Staging: 10.1.0.0/16
Dev: 10.2.0.0/16
SharedSvc: 10.10.0.0/16
On-Prem: 192.168.0.0/16
Todos con CIDRs distintos → pueden conectarse sin conflicto.

⚡ Planifica tus CIDRs antes de crear la primera VPC. Cambiar el CIDR de una VPC existente es imposible en AWS — debes recrearla.

✅ CHECKLIST DEL ARQUITECTO DE REDES

CIDRs y Subnets
  • ¿Usé rangos RFC 1918 (10.x, 172.16.x, 192.168.x)?
  • ¿Mis VPCs tienen CIDRs que NO se solapan?
  • ¿Usé /16 para la VPC (no /28)?
  • ¿Consideré las 5 IPs reservadas por subnet?
  • ¿Dejé espacio para crecer? ¿Calculé el /24 correcto?
Seguridad
  • ¿SSH (:22) solo desde IPs internas o bastion?
  • ¿Nunca usé 0.0.0.0/0 en SSH/RDP?
  • ¿Las DBs están en subnets privadas?
  • ¿Las DBs escuchan en 127.0.0.1 o IP privada?
  • ¿Usé principio de mínimo privilegio en SGs?
Conectividad
  • ¿Subnet pública tiene Internet Gateway?
  • ¿Subnet privada tiene NAT Gateway para salir?
  • ¿Route tables configuradas correctamente?
  • ¿Peering tiene rutas en ambos lados?
Aplicaciones
  • ¿Servicios internos solo escuchan en 127.0.0.1?
  • ¿Usas DNS interno en vez de IPs hardcodeadas?
  • ¿Docker: usas networks custom (no solo default bridge)?
  • ¿Puertos expuestos con -p son los estrictamente necesarios?
