CONCEPTO · ¿QUÉ ES NGINX?

NGINX: EL PORTERO DE TU SERVIDOR

Imagina un edificio de departamentos. El portero recibe todas las visitas en la entrada (puerto 80/443) y las dirige al piso correcto. Nginx hace exactamente eso con tus peticiones HTTP.

Puerto 80

HTTP sin cifrar. La puerta abierta. No segura. Usada para validación HTTP-01.

Puerto 443

HTTPS cifrado. La puerta blindada. Todo cifrado. Aquí vive tu web segura.

Redirige

80 → 443. Fuerza HTTPS en todas las visitas. Certbot lo configura automáticamente.

Sirve archivos

HTML, CSS, JS, imágenes. Web estática ultra-rápida directamente desde disco.

Nginx puede manejar 10,000+ conexiones simultáneas con muy poca RAM gracias a su arquitectura event-driven. Por eso desplazó a Apache en la mayoría de servidores modernos.

Empresas Pequeñas / VPS

Cuando la startup/empresa crece:

  • ☁️ Load Balancer (ALB) gestiona el SSL — no el servidor individual
  • ☁️ AWS Certificate Manager reemplaza a Let's Encrypt (gratis también)
  • ☁️ Nginx en EC2 recibe tráfico HTTP interno ya descifrado
  • ☁️ Auto Scaling: 1 servidor → 100 servidores sin tocar la config SSL
  • Los fundamentos son exactamente los mismos. Solo escala.
INSIGHT · ECOSISTEMA DE SERVIDORES WEB

APACHE  ·  NGINX  ·  cPANEL

Los tres aparecen constantemente en el mercado laboral. Entiéndelos.

Apache — El Clásico

Desde 1995 · Domina el hosting compartido

  • → Muy compatible con PHP / WordPress
  • → Configuración por .htaccess en cada carpeta
  • → Más lento bajo alta carga concurrente
  • → Hosting barato (GoDaddy, Bluehost) lo usa
  • → En producción moderna va perdiendo terreno
Nginx — Lo de hoy ✅

Estándar moderno · VPS · Cloud

  • → Arquitectura event-driven (no un proceso por request)
  • → Ideal: web estática, proxy reverso, microservicios
  • → Config en /etc/nginx/sites-available/
  • → Startups, VPS modernos, cloud nativo
  • → Hoy aprendes desde los cimientos ✅
cPanel — La GUI

Interfaz gráfica encima de Apache/Nginx

  • → Panel web para gestionar el servidor
  • → "AutoSSL" = Let's Encrypt por atrás
  • → Popular en hosting compartido (GoDaddy, etc.)
  • → Clientes no técnicos lo prefieren
  • → Debajo: hace lo mismo que haces hoy a mano

Clave: cPanel hace con clics lo que haces hoy con comandos. Quien entiende el fondo es más valioso que quien solo usa la interfaz gráfica.

SETUP · NGINX — COMANDOS ESENCIALES

NGINX: INSTALAR Y CONTROLAR

Todo lo que necesitas saber para operar Nginx desde el día uno

ubuntu@servidor — instalar
# Instalar Nginx (APT — Módulo 9) $ sudo apt update $ sudo apt install nginx -y # Verificar versión instalada $ nginx -v nginx version: nginx/1.24.0 # Ver estado del servicio $ sudo systemctl status nginx ● nginx.service - A high performance web server Active: active (running) since ...
ubuntu@servidor — controlar (Módulo 13)
# Iniciar / Detener / Reiniciar $ sudo systemctl start nginx $ sudo systemctl stop nginx $ sudo systemctl restart nginx # Recargar config SIN bajar el servicio $ sudo systemctl reload nginx # Habilitar al arranque del servidor $ sudo systemctl enable --now nginx # Probar que responde localmente $ curl -I localhost HTTP/1.1 200 OK
reload

Recarga config. Sin downtime. Usar tras editar nginx.conf

restart

Baja y sube el proceso. Hay micropausa. Solo si reload no funciona.

enable

Arranca al boot. Sin esto, un reinicio del server deja la web caída.

journalctl

journalctl -u nginx -f para ver logs en tiempo real.

FASE 3 · ESTRUCTURA DE NGINX

SITES-AVAILABLE + SITES-ENABLED

Nginx separa la definición del sitio (available) de la activación (enabled) usando symlinks — así puedes activar/desactivar sin borrar configs.

ubuntu@servidor — setup completo
# 1. Crear directorio de cada web (nombre = dominio) $ sudo mkdir -p /var/www/web.dominio.com $ sudo mkdir -p /var/www/app.dominio.com # 2. Subir el index.html a cada directorio $ sudo nano /var/www/web.dominio.com/index.html $ sudo nano /var/www/app.dominio.com/index.html # 3. Crear configs en sites-available $ sudo nano /etc/nginx/sites-available/web.dominio.com.conf $ sudo nano /etc/nginx/sites-available/app.dominio.com.conf # 4. Activar con symlinks a sites-enabled $ sudo ln -s /etc/nginx/sites-available/web.dominio.com.conf \ /etc/nginx/sites-enabled/ $ sudo ln -s /etc/nginx/sites-available/app.dominio.com.conf \ /etc/nginx/sites-enabled/ # 5. Verificar sintaxis y recargar $ sudo nginx -t nginx: configuration file /etc/nginx/nginx.conf test is successful $ sudo systemctl reload nginx

💡 El sitio default de Nginx sigue funcionando — es el que certbot edita primero. Los sites personalizados tienen prioridad por server_name.

📄 /etc/nginx/sites-available/web.dominio.com.conf

server { listen 80; server_name web.dominio.com; root /var/www/web.dominio.com; index index.html; location / { try_files $uri $uri/ =404; } }

📄 /etc/nginx/sites-available/app.dominio.com.conf

server { listen 80; server_name app.dominio.com; root /var/www/app.dominio.com; index index.html; location / { try_files $uri $uri/ =404; } }

⚠️ Desactivar un sitio es tan simple como borrar el symlink:
sudo rm /etc/nginx/sites-enabled/web.dominio.com.conf

FASE 5 · BAJO EL CAPÓ

¿QUÉ MODIFICÓ CERTBOT?

Certbot editó /etc/nginx/sites-available/web.dominio.com.conf automáticamente:

❌ ANTES — Solo HTTP

server { listen 80; server_name web.dominio.com; root /var/www/web.dominio.com; index index.html; location / { try_files $uri $uri/ =404; } }

✅ DESPUÉS — Certbot lo reescribió automáticamente

server { listen 443 ssl; # managed by Certbot server_name web.dominio.com; root /var/www/web.dominio.com; index index.html; location / { try_files $uri $uri/ =404; } ssl_certificate /etc/letsencrypt/live/web.dominio.com/fullchain.pem; # Certbot ssl_certificate_key /etc/letsencrypt/live/web.dominio.com/privkey.pem; # Certbot include /etc/letsencrypt/options-ssl-nginx.conf; # Certbot ssl_dhparam /etc/letsencrypt/ssl-dhparams.pem; # Certbot } server { # Certbot — redirect HTTP → HTTPS listen 80; server_name web.dominio.com; return 301 https://$host$request_uri; }

🔒 Los certificados quedan en /etc/letsencrypt/live/web.dominio.com/ — Nginx los carga en cada conexión HTTPS. Certbot también agrega el bloque de redirección HTTP→HTTPS.

FASE 6 · RENOVACIÓN AUTOMÁTICA
Fase 6

RENOVACIÓN AUTOMÁTICA — NUNCA MÁS TE PREOCUPAS

¿Cuánto dura el certificado?

Los certificados de Let's Encrypt duran 90 días. El snap de Certbot instala automáticamente un systemd timer que los renueva antes de que expiren.

¿Qué hace el timer?
  • ✅ Verifica certificados 2 veces al día
  • ✅ Si quedan < 30 días → renueva automáticamente
  • ✅ Recarga Nginx sin downtime después de renovar
  • ✅ Funciona aunque no estés conectado al servidor
Verificar renovación (Cron/Timers — Módulo 6)
# Simular renovación sin ejecutarla de verdad $ sudo certbot renew --dry-run Congratulations, all simulated renewals succeeded! # Ver el timer instalado por certbot $ systemctl list-timers | grep certbot snap.certbot.renew.timer active running

Si dry-run dice succeeded, tu SSL jamás expirará. El server se encarga. 🎉 Lo conectamos con el Módulo 6 (Cron).
